**What this proposes**
本文件提出「SLO-MO」的 MVP 設計規格，這是一款瀏覽器 HTML5 / WebGL 的 2D 橫向捲軸（體素 2.5D）動作解謎遊戲，旨在驗證「玩家操控動作極慢的三趾樹懶，面對正常速度且完全確定性的週期陷阱時，必須依賴預判與時間管理通關」的核心假設。MVP 範圍為單機單關（`level01`，含三段教學與兩個檢查點），玩家透過按住方向鍵的時間長短（經歷前搖與兩段蓄力）在放開按鍵時決定踏出小步、中步或大步（分別移動 1、2、3 格，但步幅越大則出步期間的水平受擊碰撞盒越寬），並可使用「聲納」凍結世界時鐘以預覽陷阱未來 2 秒軌跡及預先排入指令。系統會記錄步數、世界時間與死亡次數，死亡後於 1 秒內將世界時間、陷阱相位與步數回溯至最近檢查點快照，且模擬核心採用固定 60 tick/秒的純邏輯架構，確保相同的 `(tick, 指令)` 序列重播能得到一致結果。

**How the existing system works, per this document**
根據本文件所述，目前尚無既有系統運作的具體描述，本文件為從零建立 MVP 的設計規格書。文件僅於開頭提及需求來源企劃書為 `SLO-MO.txt`，且跨功能的全專案規則載於 `docs/contract.md`，但未在文件內說明這兩份外部文件的具體內容或任何既有系統架構。

### 審查發現 (Findings)

#### 1. 聲納凍結期間的輸入佇列機制與「放開即取消／放開才出步」規則自相矛盾，且佇列元素的「按住時間」起算點前後不一
- **Severity**: Blocker
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L17-L44)（`## 2. 名詞`、`## 3. 玩家動作` 第 23–35 行、`## 4. 聲納` 第 40–44 行）
- **Discrepancy Description & Rationale**:
  1. **凍結期間無法按常理排入兩個連續動作**：第 17 行與第 23 行規定玩家必須「按住方向鍵累積前搖與蓄力，放開方向鍵的那一刻才依按住時間決定步幅並開始出步」，且第 35 行明確規定「凍結期間放開該元素視為取消（世界 tick 未前進，按住時間為 0）」。然而第 43–44 行卻寫道：「凍結期間玩家可下指令；按住時間照世界時鐘算，所以凍結時暫停。解凍後，佇列第一個動作立刻開始前搖，第二個接在其後。」若在凍結期間放開按鍵就會被取消，玩家在凍結期間若想排入兩個同方向動作（例如連走兩步），第一次按下的方向鍵一旦放開就會被取消，根本無法按第二次；就算是不同方向，也必須在凍結期間同時按住兩顆方向鍵不放，直到解凍後依序等待前搖結束才放開。這使讀者無法理解凍結期間「下達並排入兩個指令」的操作流程如何成立。
  2. **佇列第 2 個元素的「按住時間」起算基準衝突**：第 23 行定義「按住時間：從按下方向鍵起算，含前搖」，第 35 行也定義佇列元素為「方向＋按下 tick」；但第 35 行後半與第 44 行卻說「輪到時開始前搖，之後繼續按住即累積蓄力」、「第一個動作立刻開始前搖，第二個接在其後」。當第 1 個動作正在進行 1.0 秒出步動作時（此時世界 tick 正在推進），若玩家按下第 2 個方向鍵進入佇列等待，第 2 個動作的「按住時間」究竟是從「按下方向鍵的 tick」起算，還是等到第 1 個動作結束、「輪到第 2 個動作的 tick」才開始計算前搖？兩處規則互相矛盾。

#### 2. 「世界時鐘唯一」與未定義的「邏輯 tick」互相衝突，且未說明聲納「凍結時間」由哪個時鐘驅動
- **Severity**: Blocker
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L14-L101)（`## 2. 名詞` 第 14 行、`## 4. 聲納` 第 40–41 行、`## 9. 暫定數值` 第 91 行、`## 架構約束` 第 101 行）
- **Discrepancy Description & Rationale**:
  1. **未定義的「邏輯 tick」與單一時鐘約束矛盾**：第 14 行定義「世界時鐘：遊戲唯一的模擬時間軸……聲納凍結時不前進」，第 101 行亦強調「世界時鐘只有一條」。但第 40–41 行卻規定「凍結時間與冷卻都以 tick 計。凍結期間世界 tick 不前進，冷卻改走邏輯 tick」。文件從未定義何謂「邏輯 tick」，也沒有說明既然存在獨立於世界時鐘之外的「邏輯 tick」，為何又宣稱世界時鐘是唯一的模擬時間軸。
  2. **凍結時間的計時基準不明**：第 40 行說「凍結時間與冷卻都以 tick 計」，但第 41 行只說「凍結期間世界 tick 不前進，冷卻改走邏輯 tick」，未說明 3 秒的「凍結時間」本身在世界 tick 停止時，是否也走「邏輯 tick」來倒數解凍。
  3. **待驗證項目語意不明**：第 91 行寫道「聲納冷卻改用 tick 後，玩家是否覺得『怪』」。若「邏輯 tick」在凍結與非凍結期間皆以固定 60 tick/秒推進，則以邏輯 tick 計算的 8 秒冷卻（含 3 秒凍結）與真實時間 8 秒完全相同，讀者無法理解為何「改用 tick」會讓玩家覺得怪（除非冷卻在某些情況下會被凍結或與其他機制掛鉤，但文件並未說明）。

#### 3. 「轉身」動作的觸發方式及其與方向鍵「前搖／出步」的互動關係未定義
- **Severity**: Major
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L33-L82)（`## 3. 玩家動作` 第 33 行、`## 9. 暫定數值` 第 82 行）
- **Discrepancy Description & Rationale**:
  第 33 行僅說明「轉身：獨立動作，不算步數」，第 82 行列出「轉身：0.4s」，但全文未說明玩家如何觸發「轉身」。當樹懶面向右方而玩家按下左方向鍵時：系統是先自動執行 0.4 秒的「轉身」、轉身完成後繼續按住才開始計算 0.8 秒的「前搖」？還是「在反方向按住時間屬於 `[0, 前搖)` 內放開」代表轉身？抑或轉身有獨立按鍵？缺乏此定義將導致無法實作方向輸入與轉身狀態機。

#### 4. 「缺口」跨不過的結果（是否致死）與死亡畫面死因清單不一致，且「步幅格數」與「缺口寬度格數」的跨越判定規則未定義
- **Severity**: Major
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L34-L61)（`## 3. 玩家動作` 第 34、36 行、`## 5. 陷阱與關卡` 第 49、53 行、`## 6. 死亡與計分` 第 59、61 行）
- **Discrepancy Description & Rationale**:
  1. **缺口失敗與逾時失敗的呈現矛盾**：第 36 行指出「小步跨不過的缺口，必須用中步或大步」，第 61 行指出「單關時間上限……超過即失敗」，但第 59 行卻規定「死亡畫面 MVP 只顯示死因（落石或電鋸）」。文件未定義玩家若用小步面對缺口會發生什麼事（是掉入缺口死亡並回到檢查點，還是被阻擋無法踏出？）。若掉入缺口會死亡，為何死亡畫面的死因僅限「落石或電鋸」而無「缺口」（以及超過單關時間上限時如何處理）？
  2. **跨越缺口的格數數學關係未定義**：第 34 行定義小、中、大步分別移動 1、2、3 格，第 36 行說明「缺口寬度以格為單位寫在關卡 JSON」，第 53 行要求「至少有一處只能用大步通過的缺口」。文件未說明移動 $N$ 格能跨過幾格寬的缺口（例如：移動 1 格的小步是移動到相鄰格，因此 1 格寬的缺口需移動 2 格的中步、2 格寬的缺口需移動 3 格的大步？還是 1 格小步即可跨過 1 格缺口？），也未說明在 1.0 秒出步動作進行中經過缺口上方時是否不進行掉落判定、僅在動作結束落腳時判定。

#### 5. 重播格式 `(tick, 指令)` 中「指令」的具體顆粒度未定義
- **Severity**: Major
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L41-L101)（`## 4. 聲納` 第 41、43 行、`## 8. MVP 完成標準` 第 73 行、`## 架構約束` 第 101 行）
- **Discrepancy Description & Rationale**:
  第 73 行要求「相同的 `(tick, 指令)` 序列重播，得到相同結果」，第 101 行寫道「重播只記錄『第幾個世界 tick 下了什麼指令』」。由於步幅取決於「按下方向鍵」與「放開方向鍵」之間累積的世界 tick 數，文件未定義重播中的「指令」是指底層輸入事件（如按下方向鍵、放開方向鍵、啟動聲納、視窗失焦），還是指結算後的出步動作。此外，聲納凍結期間世界 tick 不前進（第 41 行：「凍結中的指令以序號排序」），若重播只記錄「第幾個世界 tick 下了什麼指令」，文件未說明如何區分凍結期間內的事件順序或時間點。

#### 6. 樹懶基準水平碰撞盒寬度（`×1.0`）與地圖「格」的尺寸比例未定義
- **Severity**: Nit
- **Affected Scope**: [docs/design.md](file:///mnt/d/wsl/Arch-Dev/The-Incredibly-Slow-Survival/docs/design.md#L25-L34)（`## 3. 玩家動作` 第 25–34 行）
- **Discrepancy Description & Rationale**:
  第 32 行定義「`×1.0` 是樹懶站立時的水平受擊判定寬度」，第 34 行以「格」作為移動距離單位（1、2、3 格），但文件中未定義 `×1.0` 對應幾「格」寬（例如是否為 1 格），也未說明 1.0 秒出步動作期間樹懶的座標與碰撞盒是在格與格之間連續插值移動，還是離散跳格。
